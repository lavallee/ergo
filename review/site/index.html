Models and data: what changed, what didn't, and what to watch

How well models actually do the work of getting data in, cleaning it, joining it and querying it — read from the benchmark record rather than from vibes.

Published 2026-08-11

If you are about to point a model at a dataset you have not used before, you want to know which parts of that job you can hand over and which parts you still have to check yourself. The benchmark record answers this better than intuition does — but only if you read it with the dates attached, because the answer has changed twice in eighteen months and is still moving.

The number that is out of date the moment you quote it

In early 2025, DABstep — a benchmark of realistic data-analysis tasks built from a payments company's own documentation and files — reported that the best agent scored 14.55% on its hard split. That number travelled widely. It is a fair description of where things stood when the paper was written.

By February 2026, the top validated entry on the same hard split was 89.95%.

Both numbers are real and they measure the same tasks. Quoting either without its date describes a world that no longer exists. This is the first thing to understand about the current state of models doing data work: the headline capability numbers move fast enough that a citation ages in months, and most of what circulates is a paper baseline being read as a current ceiling.

What has actually moved

The pattern is that the tasks closest to writing correct code against a described system have improved dramatically, and the tasks that require holding a whole unfamiliar warehouse in mind have not. Extract and load went from a third to nearly all of the way in one model generation; its own authors now describe that stage as largely solved. Transformation — the part where you decide what the numbers mean — sat at 3.9% in the same benchmark.

BEAVER is the clearest limit case, because its warehouses are private and nothing in any model's training data describes them. Unaided, the best model finishes about one task in nine. Handed every subtask annotation the benchmark can supply, it finishes about three in ten. That gap between "told nothing" and "told everything" is real and large; what survives it is larger still.

What supplying knowledge is worth, and whether that is changing

The more useful question for someone deciding what to delegate is not how well a model scores, but how much better it does when you hand it what you know.

Three benchmarks answer this directly. DCA-Bench asks agents to find known defects in curated datasets, at four levels of hint. Unaided, across five configurations, agents found between 10.86% and 29.86% of them. At the top of the hint ladder — told which file and roughly what to look for — the same agents found between 67.42% and 78.28%. A two-and-a-half to six-fold improvement, from information the person handing it over already had.

ELT-Bench ran the cleaner experiment: withhold the dataset documentation entirely. Denied it, one agent completed one task and another completed none. This is the strongest available statement that the knowledge is not already inside the model.

BIRD, a text-to-SQL benchmark, measured the same thing on a different axis: it ships an "external knowledge" annotation with each question, and in 2023 supplying it was worth +20.01 points of execution accuracy.

That last number is the one worth watching, because it has moved — and the direction is the opposite of the DABstep story. An independent re-measurement in 2026, by a group with no stake in BIRD, ran six systems on the same data under the same with-and-without conditions. The gains were 8.35, 10.82, 10.96, 11.28, 12.84 and 20.86 points. Only the oldest pipeline in the set reached the original figure; every modern scaffold landed between 8 and 13.

So supplying documented knowledge about a public dataset is still worth roughly a tenth of the score. It was worth twice that three years ago. The same audit found that about 7% of the benchmark's own knowledge annotations are themselves wrong, which is a reminder that the 2023 baseline is not a fixed point either.

The distinction that survives

It would be easy to read the BIRD result as models absorbing what documentation used to supply, and to conclude that the value of writing things down is on a countdown. That reading goes further than the evidence does, for a reason worth being precise about.

Every benchmark that measures the value of supplied knowledge supplies published knowledge, about a public dataset, of the kind a model has plausibly already read. BIRD's external knowledge is an annotation about a public database. DABstep's context is a documentation set the benchmark ships. That those gains narrow as models absorb more of the web is expected, and is roughly what the numbers show.

What no benchmark has measured is the other kind. In a survey of twenty widely used open datasets, nineteen publishers shipped some form of non-data guidance and eighteen shipped guidance that changes what a reader may honestly claim — a comparability break, a suppression rule, a universe change. Only seven put it anywhere a program holding the download URL would encounter it. The rest sits in a tab inside a workbook, a footnote attached to a portal record reachable only through an undocumented endpoint, or a technical manual on a host that refuses automated clients.

One state education agency published a spreadsheet whose first tab, of sixty-three, is titled Important 2020-2021 Notes - Please Read Before Using Data in this Database, and says that pandemic-year discipline figures may not be comparable to adjacent years. Nothing in the values announces that the tab exists. A model that has never seen that file cannot know it, and a model that fetches the file by URL will not open it.

This is a different problem from capability, and it is not obviously on the same curve. Whether it is on any curve is unknown, because nobody has built the benchmark that would tell us.

Where the failures actually are

When agents fail at data work, the failures are not evenly distributed. In a hand-classified set of 4,602 text-to-SQL failures, 81.2% of execution failures came down to schema linking — picking the wrong column, or inventing one. BIRD attributes 41.6% of its errors to the same cause; Spider 2.0, 27.6%; BEAVER, 35.2%. It is the most-measured failure in the literature, and it is a failure of knowing what the columns mean.

On government open data specifically, the largest single error category is failing to apply a condition the question did not state — a date range, a status filter, or a universe restriction such as which rows in a table are totals rather than members. That category accounts for 32.4% of one model-and-scaffold pair's errors in a 2026 benchmark of 178 government datasets. The same benchmark discarded 29.9% of its candidate questions during construction, and reports that over half required knowledge external to the files.

Both categories describe the same underlying situation. The model can write the query. What it cannot do is know, from the file alone, which column means what and which rows it is allowed to add up.

What to watch

Three things would change this picture, and each is observable.

Whether the knowledge premium keeps narrowing. BIRD's with-and-without gap is the cleanest published measure of what documentation buys. It went from +20.01 to a modern-scaffold band of 8–13 in three years. If it reaches parity, models will have absorbed what published documentation used to supply, and the case for writing down anything already on the web weakens considerably.

Whether anyone measures local knowledge. No benchmark currently tests a model against a dataset whose caveats exist only in a publisher's workbook tab or a maintainer's parser comment. Until one does, claims in either direction about that category — including the one this piece makes — rest on inference rather than measurement.

Whether the ceiling moves. BEAVER's private warehouses are the hardest published case, and the gap between fully annotated and unaided has stayed wide. If a model closes it without annotations, the argument that unfamiliar systems require handed-over context weakens regardless of what happens to the benchmarks above.

What this evidence cannot tell you

Nearly every figure here is a benchmark's authors reporting results on the benchmark they built. That is normal for the field and it is not a reason to dismiss the numbers, but it means independent corroboration is rare: in the set behind this piece, exactly one measurement was made by a party with no stake in the benchmark it re-measured. BEAVER cannot be independently re-measured at all, because its warehouses are private — the property that makes it a good test also makes it unauditable.

Benchmarks also measure benchmark tasks. Scores on curated questions with known answers say less about an open-ended analysis than their precision suggests, and several of these benchmarks have had their ground truth disputed by their own communities.

There is a survivorship problem too. Benchmarks that stay in circulation are disproportionately the ones models have not solved; the ones that got solved stopped being cited. A survey of live benchmarks over-represents unsolved problems by construction, which means the picture here is probably more pessimistic about current capability than the truth.

And the central distinction of this piece — published knowledge closing, local knowledge untouched — may be a timing argument in disguise. If a future model has crawled enough of the web to know that education workbook's first tab, local knowledge simply becomes published knowledge on a lag. The counter-argument is narrow and technical: the tab in question sits inside an .xlsx behind a JavaScript-rendered index, which is a claim about crawlability rather than about intelligence.

What follows for the work

If you are deciding what to delegate: the parts of a pipeline that amount to writing correct code against a described system are, on the current evidence, reasonable to hand over and getting more so. The parts that depend on knowing what a column means, which rows are totals, which year broke comparability, or why a value is suppressed rather than missing are where agents fail most and where supplying what you know still buys the most.

The practical consequence is that the check worth keeping is not "did it write good code" but "did it know what it was looking at." And since the publisher usually wrote that down somewhere the download does not point, the cheapest useful habit available is going to find it before the first fetch rather than after the first wrong number.
