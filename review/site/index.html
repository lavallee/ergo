Models and data: what changed, what didn't, and what to watch

How well models actually do the work of getting data in, cleaning it, joining it and querying it — read from the benchmark record rather than from vibes.

Published 2026-08-11 · figures verified 2026-08-11

If you are about to point a model at a dataset you have not used before, you want to know which parts of that job you can hand over and which parts you still have to check yourself. Public benchmarks answer this better than intuition does — but only with the dates, the models and the exact task attached, because all three change the answer.

Why a number you read last year is probably wrong

Start with one benchmark, because its history shows the problem cleanly. DABstep is a set of 450 data-analysis questions built by Adyen, a payments company, from its own internal documentation and files — the kind of task where answering correctly requires reading a manual, not just writing a query. Its questions are split into an easy tier and a hard tier, and the hard tier is where systems separate.

In April 2025, the best configuration the authors tested — OpenAI's o4-mini, prompted to reason, wrapped in a ten-step loop that let it alternate between thinking and running code — scored 14.55% on the hard tier. That number travelled widely.

By February 2026, the top entry on DABstep's validated leaderboard scored 89.95% on the same tier. Validated matters: the board has a checked tier and an open one, and the open tier currently contains multiple undisclosed entries claiming 100%, which makes it useless as evidence.

Two things follow. First, quoting 14.55% today describes a world that ended eighteen months ago. Second, that 89.95% is itself now frozen — DABstep has closed validation to new submissions pending a second version, so the number cannot move even if systems improve. A live benchmark and a live leaderboard are not the same thing.

It is also not one model. The entry is NVIDIA's KGMON Data Explorer, a pipeline in which Claude Opus 4.5/4.6 writes helper functions offline, Haiku 4.5 executes them, and Opus or Sonnet 4.6 reviews the result. Attributing it to a single model would be wrong, and this is typical. Almost every score in this piece belongs to a scaffold — the harness of prompts, tools and retry logic wrapped around one or more models — and swapping the scaffold can matter as much as swapping the model. Where a score is quoted below, the scaffold is named alongside the model.

The benchmarks, and what each one actually asks

"Can models do data analysis" is too coarse a question to have an answer. The benchmarks below test genuinely different jobs, and a system strong at one can be weak at the next. Here is the cast used in this piece.

  • DABstep — analysis questions over a firm's own files and documentation. Tests whether a model reads the manual.
  • BIRD — text-to-SQL over 95 databases. Ships an "external knowledge" note with each question, so it can be run with and without domain hints. Scored by execution accuracy: does the generated query return the right rows.
  • Spider 2.0 — text-to-SQL at enterprise scale, on real warehouses averaging hundreds of columns per database. Three tracks: one on Snowflake, one general, and one that asks for a working dbt project — dbt being the tool teams use to define warehouse transformations as version- controlled SQL.
  • BEAVER — analysis against private company warehouses no model has been trained on. It also scores five sub-skills separately, which is why it is the best evidence about where capability breaks.
  • ELT-Bench — building a pipeline, not answering a question. ELT is three stages: extract data from sources, load it into a warehouse, then transform it into modelled tables. The stages are scored separately.
  • DCA-Bench — finding known defects hidden in curated datasets, at four levels of hint, from none to a specific pointer.
  • LongDA — 505 questions drawn from 30 official publications across 17 US federal surveys, answered against the real microdata and its real codebooks, which average 263,500 tokens. The closest published analogue to working with government statistics.
  • DataGovBench — question-answering over 178 government open-data files, published July 2026.

What has moved since early 2026

The pattern: work that amounts to writing correct code against a described system has improved sharply, sometimes on a model upgrade alone. ELT-Bench's extract-and-load stage went from a third to nearly all of the way with no change but a newer Claude, and its authors now describe that stage as largely solved. Work that requires understanding an unfamiliar system has barely moved: the transformation stage of the same benchmark, where you decide what the numbers mean, sits at 22.66%.

Where capability is jagged

BEAVER is the most informative benchmark here because it scores five sub-skills separately on the same tasks. Its warehouses are private company systems, so nothing in any model's training data describes them — which is what makes the profile below a clean read on what models can work out from a schema alone.

The order is the finding. Picking the right table is largely solvable from the schema. Picking the right join key is much harder, because a schema rarely says which of several plausible columns actually relates two tables. And domain knowledge — what a column means in the business that produced it — is where models do worst, at 20.4.

Other benchmarks show the same shape from different angles. On the government open-data benchmark, the largest single error category is failing to apply a condition the question never stated — a date range, a status code, or which rows in a table are totals rather than members — accounting for 32.4% of one system's errors (Gemini 2.5 Flash with its Answer Agent scaffold). On a table-reasoning benchmark, the same models score above 90 on fact-checking and numerical reasoning while sitting at 61.4 on open data analysis.

What handing over documentation is worth

The practical question is not how models score, but how much better they do when you give them what you know. Seven benchmarks run that comparison directly, and the answer ranges from decisive to almost nothing — which is the first thing worth noticing. What you hand over matters far more than that you hand something over.

The row to read first is the human one. Given BIRD's evidence note, human data engineers and database students scored 92.96; without it, 72.37. They lose more than twenty points to the same missing information. Whatever else these numbers show, the knowledge is not a crutch for weak models — it is a requirement of the task.

LongDA is the most relevant result published. Its questions come from real US federal survey publications and are answered against the real microdata with the real codebooks — the situation anyone working with government statistics is actually in. The best system, GPT-5 under the authors' ReAct-based scaffold with a documentation-search tool, reaches 69.16%. Delete only that documentation-search tool, changing nothing else, and it falls to 58.30% — eleven points, from the ability to look something up. The benchmark requires choices like selecting the correct survey weight from among several, which no amount of general knowledge supplies.

DCA-Bench shows the same effect as a gradient. Asked to find known defects with no hints, its best configuration (DeepSeek-R1 as curator) found 29.86%; given the most specific hint, the same model with retrieval found 78.28%.

ELT-Bench ran the blunt version: withhold the dataset documentation entirely. Denied it, one agent completed a single task and another completed none.

BIRD supplies the counterweight. Its external-knowledge annotation was worth +20.01 points in 2023. An independent re-measurement in 2026 — by a group with no stake in the benchmark, running six systems under the same conditions — found gains of 8.35, 10.82, 10.96, 11.28, 12.84 and 20.86 points. Only the oldest pipeline reached the original figure; every modern one landed between 8 and 13.

At the other end sits ScienceAgentBench, where an expert note added 1.9 points — a reminder that supplying something guarantees nothing. The spread from +1.9 to +48.4 is not noise; it tracks how closely what was handed over matched what the task actually required.

So the premium for supplying published knowledge about a public dataset is real and appears to be shrinking. The premium for supplying documentation the model cannot otherwise reach — LongDA's eleven points, measured this year on federal codebooks — is not shrinking, because nothing has absorbed it.

The wider field

The benchmarks above are the ones with results bearing directly on the argument. They are a fraction of what exists. A broader scan turned up more than thirty active evaluations touching data work, and the shape of that set is itself informative — several categories are crowded, and the ones closest to public-statistics practice are nearly empty.

Two things stand out. Entity matching and schema matching are close to saturated — one entity-matching set of 755,540 pairs is answered at 98.95 F1 by GPT-4o with no scaffold at all — while anything requiring sustained state falls apart: one enterprise benchmark records 0% execution accuracy by the third turn across every model it tested. And the validity layer is barely explored. Whether a model's conclusion is statistically supported, rather than whether its code ran, is measured by two benchmarks, both from this year, both scoring badly.

What nobody is measuring

Two absences are worth naming, because they bound what any of this can tell you.

Nothing tests finding the data. Every benchmark above hands the model its files. In practice the first and often hardest step is working out which dataset answers the question, and which of its several published faces to fetch.

Nothing scores the things that make official statistics hazardous. There is no benchmark measuring whether a model respects suppression rules, distinguishes numeric sentinel codes from real values, applies survey weights correctly as a scored axis, or produces design-based standard errors. LongDA comes closest and explicitly puts variance estimation out of scope. These are the errors most likely to produce a confident, publishable, wrong number — and there is no evidence either way about how often models make them.

The large caveat: some of this is the benchmarks failing

Two independent audits this year found that a substantial share of what gets recorded as model failure is benchmark error.

A CIDR 2026 paper re-examined the ground truth of the leading text-to-SQL benchmarks and reported annotation error rates of 52.8% in BIRD's Mini-Dev split and 66.1% in Spider 2.0-Snow. On corrected data one system rose from 62% to 81% and moved from fourth place to first. Separately, ELT-Bench-Verified re-checked its own benchmark and found that 82.7% of failed tasks contained an error attributable to the benchmark rather than the agent; fixing them moved the transformation score from 22.66% to 32.51% without touching the system.

This does not invalidate the direction of any finding above, but it should make you distrust small differences and any leaderboard ranking decided by a few points.

Two more things to hold lightly

Nearly every figure here is a benchmark's authors reporting results on the benchmark they built. That is normal, and it means independent corroboration is rare — the BIRD re-measurement above is the exception, not the rule. BEAVER cannot be independently re-measured at all: its warehouses are private, which is exactly what makes it a good test and what makes it unauditable.

And benchmarks that stay in circulation are disproportionately the ones models have not solved. The ones that got solved stopped being cited. Any survey of live benchmarks over-represents unsolved problems, so the picture here is probably gloomier than the truth.

What to watch

Whether the published-knowledge premium keeps shrinking. BIRD's with-and-without gap went from +20.01 to a modern-scaffold band of 8–13 in three years. If it reaches parity, models will have absorbed what published documentation used to supply.

Whether anyone measures the unreachable kind. LongDA is the first benchmark to price documentation access on real official data. One result is not a trend, and until there are more, claims about that category — including this piece's — rest on a single measurement.

Whether the jagged profile flattens. If domain knowledge climbs from 20.4 toward the 70 that table retrieval already reaches, the argument that unfamiliar systems require handed-over context weakens sharply.

What follows for the work

On the current evidence, the parts of a pipeline that amount to writing correct code against a described system are reasonable to delegate and getting more so. The parts that depend on knowing what a column means, which rows are totals, which year broke comparability, which weight to apply, or why a value is suppressed rather than missing are where systems fail most, where supplying what you know buys the most, and where nobody has measured how often things go wrong.

The check worth keeping is therefore not "did it write good code" — increasingly it does — but "did it know what it was looking at." And since that knowledge usually exists, written down by the publisher somewhere the download does not point to, going to find it before the first query costs less than discovering its absence in a published number.
